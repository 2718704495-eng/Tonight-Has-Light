# 2026-08-24-wechat-urlsearchparams-appid-preview-v2：微信小游戏启动查询解析兼容与 AppID 隔离预览

## 一句话结论

v1 在微信小游戏环境首帧因为缺少浏览器 `URLSearchParams` 崩溃；v2 改成纯字符串查询解析后，使用已登记 AppID 的隔离副本可在微信开发者工具小游戏模式运行，并已在明确授权下生成新的临时预览二维码，真机仍待验证。

## 1. 先讲业务：这次到底做了什么

- 谁会遇到这个场景：项目负责人准备用已有已登记 AppID 在微信开发者工具里跑《今夜有灯》的小游戏包。
- 他想做什么：不重新等小程序审批，先用旧 AppID 做开发阶段预览验证。
- 原来是什么情况：v1 包可以生成历史预览二维码，但微信小游戏模拟器启动即报 `URLSearchParams is not defined`，二维码和包都必须废弃。
- 现在是什么情况：v2 不再依赖这个浏览器 API，小游戏模拟器 0 error，夜空、成年人背影、猫、小屋、两朵花可见。
- 为什么要改：小游戏 JavaScript 环境不是完整浏览器环境，浏览器里能用的 Web API 不能默认存在。
- 验收结果：`npm run verify` 通过，32 个 Cocos 测试通过；v2 证据包和包体哈希通过；v2 `preview` 成功并生成二维码。Gate C 仍是 `BLOCKED`，因为没有真机证据。

## 2. 再讲底层：程序是怎么做到的

### 2.1 底层原理一句话

本质上就是把“读 URL 查询参数”从浏览器对象 `URLSearchParams` 改成项目自己的小函数，启动时只判断两个固定参数是否要求减少动态。

### 2.2 调用链

| 顺序 | 谁调用谁 | 传入什么 | 做了什么 | 输出或状态变化 |
|---|---|---|---|---|
| 1 | Cocos 场景加载 `OutdoorGateCRig.onLoad` | 当前运行环境的 `location.search` | 询问是否开启减少动态 | 得到布尔值 |
| 2 | `startupRequestsReducedMotion` 调 `requestsReducedMotionFromSearch` | 查询字符串或空值 | 不访问浏览器专属 API，只做字符串扫描 | 不会因缺少 `URLSearchParams` 崩溃 |
| 3 | `requestsReducedMotionFromSearch` | `reducedMotion`、`motion` 两类参数 | 只接受首个同名参数，支持 `+`、百分号解码，坏编码不抛错 | 返回是否减少动态 |
| 4 | 构建产物 `assets/main/index.js` | TypeScript 编译结果 | 进入微信小游戏包 | v2 生成代码中没有 `URLSearchParams` |
| 5 | AppID 隔离副本 | 仅 `project.config.json` | 写入用户已登记 AppID | 源构建和冻结 Release 不被污染 |

### 2.3 改动前后对比

- 改动前：启动查询解析依赖 `URLSearchParams`，微信小游戏环境缺少它时首帧崩溃。
- 改动后：启动查询解析由 `requestsReducedMotionFromSearch` 完成，坏编码和缺参数都安全返回。
- 真正发生变化的那一步：只有减动查询解析和重新编译后的 `assets/main/index.js` 变了，视觉、音频和素材未变。

### 4.1 核心技术

#### 小游戏环境兼容

- 先用白话说它是什么：同一段 JS 在浏览器和微信小游戏里能用的全局对象不完全一样。
- 本次具体怎么用：不再假设 `URLSearchParams` 存在，只保留项目需要的两种查询参数判断。
- 为什么这样用：业务只需要知道是否减少动态，不需要完整 URL 标准库。
- 这样做的好处：启动更稳，依赖面更小，坏输入不会打断首屏。
- 它的限制或代价：这个函数不是完整 URL 解析器，只服务当前两个参数。
- 相关字段、函数、接口或文件：`requestsReducedMotionFromSearch`、`decodeFormQueryComponent`、`outdoor-gate-c-rig.test.ts`。
- 证据：生成的 v2 微信包不含 `URLSearchParams`；`npm run verify` 通过，相关测试覆盖无浏览器全局对象的解析。

#### AppID 隔离副本

- 先用白话说它是什么：把真实 AppID 只放进一份临时副本，正式冻结包继续保持通用测试 ID。
- 本次具体怎么用：v2 构建源与 AppID 副本只有 `project.config.json` 不同；冻结 Release 的配置哈希仍保持锁定值。
- 为什么这样用：既能用用户登记过的 AppID 做本地微信验证，又不会污染已冻结证据链。
- 这样做的好处：回溯清楚，QA 可以独立确认真实 AppID 没有散落到文档和源包。
- 它的限制或代价：微信 `preview` 是外部提交，必须另行授权；本轮已取得授权并执行，但二维码生成不等于真机通过。
- 相关字段、函数、接口或文件：`project.config.json`、v2 构建目录、v2 AppID 隔离副本。
- 证据：目录差异检查显示 v2 源包与 AppID 副本只差配置文件；冻结 Release 配置哈希保持锁定。

### 4.2 基础或顺带用到的知识

- **首个同名参数语义**：测试用标准 `URLSearchParams.get` 当参考，保证多个同名参数时只看第一个值。
- **百分号解码容错**：坏编码不抛错，当前业务只认精确 ASCII 键值，无法解码时保留原字符串更安全。
- **哈希校验**：证据文件和包体文件都用 SHA-256 清单复查，避免后来手工修改后证据失真。
- **构建日志判断**：中间子进程 `SIGTERM` 后若后续任务成功并出现最终 Finished，可以作为已解释构建噪声记录，不能单独当失败。

### 4.3 想过但没有采用的技术

- **引入 URLSearchParams polyfill**：未采用。适合项目需要完整 URL 标准行为时；本次只读两个参数，引入 polyfill 会增加包体和依赖面。
- **修改冻结 Release 的 AppID**：未采用。会污染已冻结证据链，不利于 QA 判断 v2 到底改了什么。

## 6. 为什么这样实现

- 最关键的实现选择：用小而明确的查询解析函数替代浏览器 API。
- 为什么当前方案够用：当前启动逻辑只关心 `reducedMotion=1` 和 `motion=reduced`。
- 为什么没有必要做得更复杂：完整 URL 解析会带来更多兼容和包体成本，但不增加当前业务价值。
- 什么情况下当前方案会不够用：未来如果要解析嵌套 URL、数组参数、排序或完整标准行为，就需要引入更完整的解析器或平台确认。
