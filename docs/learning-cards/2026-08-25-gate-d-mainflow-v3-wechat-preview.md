# gate-d-mainflow-v3-wechat-preview-20260825：把 D-lite V3 主功能包生成微信手机预览二维码

## 一句话结论

已经把 `gate-d-mainflow-v3-dev` 生成了可扫码的微信 `preview` 二维码，用户可以用手机测试主流程；这不是 `upload`、体验版、审核版或线上发布。

## 1. 先讲业务：这次到底做了什么

- 谁会遇到这个场景：项目负责人想让用户直接拿手机感受当前小游戏主流程。
- 他想做什么：复用已经登记的旧 AppID，生成一版手机能扫码玩的测试包。
- 原来是什么情况：D-lite V3 只有本地微信构建记录，未远程预览；旧 v2 二维码因为画面停帧已废弃。
- 现在是什么情况：新的二维码已生成，指向 `gate-d-mainflow-v3-dev` 主功能包。
- 为什么要改：浏览器或本地构建不能替代手机上对声音、动效、触控和微信环境的第一轮体验。
- 验收结果：本地 75 项验证通过，微信 preview 成功输出二维码；真机游玩反馈仍待用户测试。

## 2. 再讲底层：程序是怎么做到的

### 2.1 底层原理一句话

本质上是把 Cocos 已构建好的 `wechatgame` 目录交给微信开发者工具 CLI 的 `preview` 命令，由微信工具提交临时预览包并写出二维码图片。

|---|---|---|---|---|

- 改动前：只有本地包，用户不能直接扫码玩 D-lite V3。

- 真正发生变化的那一步：执行了微信 `preview` 外部操作；没有重新构建、上传体验版或发布。

### 4.1 核心技术

#### 微信开发者工具 CLI preview

- 先用白话说它是什么：这是微信开发者工具自带的命令行预览功能，可以把本地小游戏目录变成手机扫码测试二维码。
- 本次具体怎么用：传入 `--project` 指向 Cocos 生成的 `wechatgame` 目录，并用 `--qr-format image --qr-output` 保存二维码。
- 为什么这样用：用户要手机上玩一版测试，`preview` 正好对应临时扫码测试；`upload` 会进入版本管理链路，权限和含义更重。
- 这样做的好处：可快速真机体验，不触碰审核和正式发布。
- 它的限制或代价：二维码是临时预览，不能证明 Gate C/E 真机验收通过，也不能替代正式体验版或审核版。
- 相关字段、函数、接口或文件：`/Applications/wechatwebdevtools.app/Contents/MacOS/cli`、`preview-qr-gate-d-mainflow-v3.jpg`。
- 证据：CLI `preview --help` 显示 `--project`、`--qr-format`、`--qr-output`；本次 preview 输出 `preview` 成功。

#### Gate 状态边界

- 先用白话说它是什么：项目里每一版都必须说明它到底通过了什么、没通过什么。
- 本次具体怎么用：文档把当前状态写成 `PREVIEW QR GENERATED / REAL DEVICE USER TEST PENDING`，同时保留 Gate C/E 和正式 Gate D 为 `BLOCKED`。
- 为什么这样用：手机能扫码玩，不等于正式 UI、正式素材、性能、低亮和生命周期都过关。
- 这样做的好处：后续不会把临时二维码当成审核发布依据。
- 它的限制或代价：文档会比“发个码”多一步，但能防止团队串线。
- 相关字段、函数、接口或文件：`docs/PROJECT-MEMORY.md`、`docs/GATE-D-MAINFLOW-V3-WECHAT-PREVIEW-20260825.md`。
- 证据：项目记忆已新增本次预览记录和边界。

### 4.2 基础或顺带用到的知识

- **包体检查**：用文件字节总数和微信 preview 输出的包体表确认包大约 3.6 MB，适合先做预览测试。
- **SHA-256 哈希**：给二维码文件记录哈希，后续能确认用户扫的是哪一版。
- **CLI 退出码差异**：微信 `preview` 第一次内部失败但命令退出码仍为 0，所以不能只看 shell 退出码，要看是否真正输出 `preview` 成功和二维码文件。

## 6. 为什么这样实现

- 最关键的实现选择：只对当前 D-lite V3 包执行微信 `preview`。
- 为什么当前方案够用：用户现在要手机游玩测试，不需要进入审核或线上发布。
- 为什么没有必要做得更复杂：没有新代码改动，也没有新的正式视觉资产可入包。
- 什么情况下当前方案会不够用：如果要给更多测试者长期访问、设为体验版或提交审核，就需要另一次明确授权和更完整真机 QA。

## 9. 自测题

### 题 1

为什么这次用 `preview`，不用 `upload`？

我的回答：

参考答案：因为用户当前要手机扫码测试一版，`preview` 生成临时二维码即可；`upload` 会进入版本管理和体验/审核链路，需要单独授权。

### 题 2

为什么 shell 退出码为 0 也不能直接判断微信预览成功？

我的回答：

参考答案：第一次微信 CLI 内部返回 code 10，但 shell 退出码仍为 0 且没有二维码文件；必须看输出是否显示 `preview` 成功，并确认二维码文件存在。

### 题 3

这次二维码证明了什么，不能证明什么？

我的回答：

参考答案：证明 D-lite V3 包已被微信预览服务接受并生成扫码入口；不能证明真机性能、低亮、生命周期、正式 UI 或正式 Gate D 已通过。

### 题 4

为什么要记录二维码 SHA-256？

我的回答：

参考答案：为了固定这次预览二维码的身份，后续能确认用户扫的是哪一版，避免和旧 v2 停帧二维码混淆。

### 题 5

当前室内暖屋批准图有没有进入这次微信包？

我的回答：

参考答案：没有。`INDOOR-N01-PROTOTYPE-V1` 的批准图只允许用于隔离的本地浏览器可丢弃样片，不进入正式微信包；这次微信包仍是 D-lite 功能壳。
